# Building, crafting and item interaction audit

## Scope and evidence

Read-only source audit of the **pre-change packaged Remastered game** at:

`/Users/kiwimango/Downloads/Dungeon-Master-master/standalone/remastered/dist/Dungeon Master Remastered/Source/game`

This note describes existing handlers and their written conditions. **No game was built, launched or tested for this audit.** Menu presence does not prove a complete working interaction. Proposed mobile decisions are explicitly separated below. This is an interpretation guide to the complete action/option catalog, not a replacement for that catalog or a recipe-by-recipe certification.

The include list is authoritative: [Cave Crawlers.dme:23](</Users/kiwimango/Downloads/Dungeon-Master-master/standalone/remastered/dist/Dungeon Master Remastered/Source/game/Cave Crawlers.dme:23>) includes `Code/Items/CraftingStations.dm`, `Code/Turfs.dm`, `Code/Click.dm`, the building files, food/equipment handlers and the original Remastered QoL/Actions modules. It does **not** include the older `Code/Mob/Workshop/` files. In particular, the old carpentry menu's “Spear Shaft” should not be treated as a current workshop recipe. The alternate `BuildAt` implementation at the top of `Building.dm` is inside a block comment; active terrain building starts in `turf/MouseDrag` at line 160.

Packaged DME SHA-256: `c3fbbf5f8a3d225f481daa1a29b1ea8efad56416769baa32007f7891ad8855ad`.

## Workshop and crafting menu families

Most workshops reject Spiders and wagons. Many recipe bodies require `M in range(1,src)`, but range checks are not consistent across all families. Many run `prob(skill * 4)`, consume inputs on failure, and put successful output **on the unit's tile**, not in its inventory. There are also batch, in-place mutation and special sacrifice recipes.

## Ambiguities and side effects requiring live comparison

These are **source findings/questions**, not reproduced runtime failures:

1. **Mixed selection is not uniformly a batch action.** Many handlers loop selected units but `return` at the first ineligible actor, first success or cancellation. Some nested prompts repeat per actor. Define the intended actor explicitly before offering “all selected” buttons.
2. **Presence versus consumption:** floor branches differ from walls/bridges; quality, byproducts, skill progression, hunger/mana and captivity are additional costs. A normalized recipe table must preserve these distinctions or mark deliberate design changes.
3. **Workshop destruction is broader than its label:** helpers at [Code/Items/CraftingStations.dm:1](</Users/kiwimango/Downloads/Dungeon-Master-master/standalone/remastered/dist/Dungeon Master Remastered/Source/game/Code/Items/CraftingStations.dm:1>) delete *all same-family workshop mobs in view(3,unit)*. Usually this removes both halves, but could remove neighboring stations too; there is no owner filter in those helpers.
4. **Range/ownership vary:** Campfire cooking, Smelter processing and some Melter paths lack the same proximity guard used by ordinary recipes. Other operations check `view`, `range`, possession or ownership at different stages. Menus can remain open while the unit/target changes or dies. Test stale-target and cancellation behavior before reusing a handler asynchronously.
5. **Inventory accounting has two styles:** [Code/Items/Item Procs.dm:44](</Users/kiwimango/Downloads/Dungeon-Master-master/standalone/remastered/dist/Dungeon Master Remastered/Source/game/Code/Items/Item Procs.dm:44>) checks `item.weight + carried_weight` and applies silver/flying restrictions; older item menus commonly check only `carried_weight <= capacity` then add the item. Do not assume all items have equivalent pickup behavior.
6. **The Smelter failure branch deletes an input and then formats `S.name`** ([Code/Items/CraftingStations.dm:5487](</Users/kiwimango/Downloads/Dungeon-Master-master/standalone/remastered/dist/Dungeon Master Remastered/Source/game/Code/Items/CraftingStations.dm:5487>)). It is a source-level lifetime hazard, not verified here. Batch failure handling also differs from ordinary recipes that stop after one failure.
7. **Destructive choices can look ordinary:** Melter deletion, evil sacrifice, gargoyle soul creation, potion transformation/death, poison drinking, grave robbing and ground/linked-stair destruction need clear scope in the interaction plan.
8. **Surface names can mislead:** “Meth Lab” is the potion-station build label; “Melter” is disposal; “Cure Vampirism” appears to cure infection, not simply reverse every established vampire. Strings and state are intertwined; changing labels must not change dispatch identifiers.
9. **Recipe correctness needs outcome checks:** full-armour sets, arrows/quivers, multi-ingredient recipes, skill/quality thresholds, source-versus-selected `Race`, output ownership and save/reload should each be observed. A log that a proc was entered is insufficient.
10. **No mobile route is certified by this audit:** physical taps, old double-click item menus, drag building, keyboard placement cancellation and camera/view changes need a route-by-route test after the plan is approved.

## Proposed mobile decisions — not current behavior

- Keep a **selected actor plus tapped target** context: “Worker → Carpentry → available recipes”, “Worker → flask → fill/drink”, “Worker → locked door → unlock/pick/attack”. Show why an action is unavailable instead of hiding all context.
- Model each action with entry route, eligible actors, target/possession/range, requirements versus consumed inputs, chance/quality, output location, side effects, cancellation and batch behavior. Build this adapter from the complete catalog before replacing legacy handlers.
- Use a large contextual primary action for an obvious reversible operation; retain a readable secondary menu for alternatives. Do not reduce rich containers, doors or workshops to one guessed action.
- Give construction an explicit mode, ghost footprint, material/requirement readout and visible cancel. Distinguish tap-to-place from drag painting and from selection; explain paired stairs and upper-layer support effects.
- Offer recipe search/categories and batch quantities, but only after each recipe's real conservation/output semantics are recorded. A new production queue is a design extension, not a description of this packaged source.
- Separate deliberate destructive choices from ordinary selection/pickup. Show the actual affected station area, item set or unit; keep existing confirmation intent where present.
- Keep uncommon racial, magic, captive and item-specific interactions reachable through context. A smaller mobile HUD should reduce navigation, not remove existing mechanics.

Implementation remains paused. This document is planning evidence only.
